# LoRA 与码本初始化实验记录

> **状态：五个实验全部完成**（E1–E5，2026-09-16）。
> 本文档独立于 `PROGRESS.md`，作为这条实验线的完整叙事。稳定后并入。
>
> **一句话**：给新增的 SID token 用 RQ-KMeans 码本向量做 embedding 初值，使 LoRA 的收敛速度提升 **1.82×**，
> 测试集 HR@50 从全参的 **86.1%** 提升到 **99.2%**、HR@1 从 **37.4%** 提升到 **91.3%**；
> **而同样的初始化对全参几乎无影响（−1.79%）**——说明该问题的根源是**容量不足**，不是初始化不好。
>
> **机制归因**：打乱码本对应的对照保住了 **83–95%** 的提升 → **主要机制是"把新 token 放进 SID 该在的
> 向量区域"（分布效应）**，token 级精确语义只有 2–3% 的额外增量。

---

## 0. 来龙去脉

### 0.1 起点：LoRA 是作为"效率消融"引入的

主线是 MiniOneRec 的三段式流水线：**多任务 SFT → GRPO 强化学习 → 受限 beam search 评估**。
SFT 的 of-record 结果是 `outputs_ds/final_checkpoint`（best-828，测试集 HR@50 = 9.66%），它是 RL 的起点模型。

LoRA 的**原始定位**是回答一个效率问题：

> **用 ~1.8% 的可训练参数，能接近全参微调的效果吗？**

它从一开始就是**与主线并列的消融**，不替换任何主线产物（物理隔离到 `outputs_sft_lora/`）。

### 0.2 第一个绕不过去的问题：新增 token

这个项目有个特殊性——**SFT 前要向 tokenizer 注入 783 个 SID token**：

```
原始词表 151669  →  注入 783 个 SID token  →  152452
783 = 256×<a_*> + 256×<b_*> + 256×<c_*> + 15×<d_*>
```

这直接决定了 LoRA 的实现形态：

| 问题 | 后果 |
|---|---|
| embedding 必须扩到 152452 行 | 新行不能冻结，否则 SID 永远学不出来 |
| `tie_word_embeddings=True` | lm_head 与 embed_tokens 是**同一块 tensor**，写入即双向生效 |
| PEFT 的 `get_peft_model` 会冻结所有非 LoRA 参数 | **必须先 `get_peft_model`、后打开 embedding**（顺序反了会静默冻结 SID 行） |

**因此 LoRA 的配置里，"embedding 开不开"变成了一等公民**，而不是默认冻结。

### 0.3 E1 的结果：一个漂亮的负结果

LoRA 跑完后（详见 §2），结论是**不划算**：

- 显存只省 **0.54 GiB（2.7%）**——因为 LoRA 和 ZeRO 分片作用在同一处，收益不可叠加
- 测试集 HR@50 只有全参的 **86.1%**，HR@1 只有 **37.4%**

**关键观察**：差距随 K **单调缩小**（K=1 差 62.6% → K=50 差 13.9%）。

> 这说明 LoRA 学到的是"**粗粒度**"——知道答案大致在哪，但排不到第一。
> 一句话概括：**LoRA 适合让模型适应新风格/新领域，不适合教它一整套全新的符号系统。**

### 0.4 由此想到：把"学符号"这件事外包出去

上面的诊断直接指向一个补救方案：

> 如果 LoRA 的瓶颈是"学不会新符号系统"，那**先把新符号的语义初值给它**，不就行了？

而项目里**恰好有这么一个现成的语义源**：RQ-KMeans 的码本。

```
RQ-KMeans 码本:  codebook_0/1/2  shape (256, 1024)
Qwen3-0.6B:      hidden_size = 1024
```

**维度相同只是巧合，真正的问题是：这两个空间语义上对得上吗？**

实测（2026-09-14）：

| 检验 | 结果 | 随机基线 |
|---|---|---|
| 线性对齐留出 R²（PCA→64 + 岭回归） | **0.4032** | −0.0348 |
| 相似度结构 Spearman | +0.2160 | −0.0007 |
| level-0 簇命中率 | **47.3%** | 0.39%（122×） |
| level-1 严格检验（固定 `<a_x>` 上下文） | **82.4%** | 25.0%（3.3×） |

**两空间实质对齐 → 码本向量可以当 embedding 初值。** 这就是 E2 的由来。

## 1. 三个实验的关系

```
E1  LoRA + resize 初始化              ← 基线，已完成 ✅
E2  LoRA + 码本初始化                 ← 已完成 ✅✅   （大幅提升）
E3  全参 + 码本初始化                 ← 已完成 ✅    （几乎无影响，略负）
E4  全参 + 码本初始化 的测试集评估     ← 已完成 ✅
E5  LoRA + 码本**打乱**初始化（对照）  ← 已完成 ✅    （保住 83–95%，机制归因）
```

**E1 vs E2 是干净 A/B**：同 seed、同数据、同超参、同卡数，**唯一变量 = `INIT_EMB`**。
**E3/E4 回答另一半问题**：全参的容量本来就够，码本对它是多余的还是仍有增益？

### 3.3 一个反直觉的观察：eval_loss ≠ 检索质量

| | best eval_loss | HR@50 |
|---|---|---|
| 全参 SFT | **2.0900** | 0.096579 |
| LoRA+码本 | **2.4151** | 0.095774 |

**eval_loss 差 0.33，检索指标几乎持平。**

原因：`eval_loss` 是三个 SFT 任务（NTP + sid↔title + hist↔title）全部 token 的平均，而测试集只考 SID 检索。
**LoRA 可能在 title 生成上明显更差，但在 SID 预测上追平了全参。**

> **教训：SFT 的 eval_loss 不能当作下游检索质量的代理指标。**

## 4. 实现要点

### 4.1 ⚠️ 尺度：目标是 resize 默认初始化的范数（≈0.30），**不是**老词表范数（0.926）

这是本实验**最大的一个坑**，初版实现选错了尺度目标，实测代价极大：

| 目标范数 | 新 token 区间 logits mean/std/max | 首步 loss |
|---|---|---|
| resize 基线（MVN 初始化） | +3.55 / 3.20 / 10.50 | 15.66 |
| 0.05 | −0.12 / 0.35 / 0.87 | 13.80 |
| 0.2 | −0.48 / 1.40 / 3.47 | 13.37 |
| **0.3026（= resize 的范数）** | −0.70 / 2.13 / 5.34 | **13.18** |
| 0.5 | −1.22 / 3.56 / 8.81 | 15.03 |
| **0.9262（初版，错）** | −2.26 / 6.61 / 16.62 | **24.13** |

**机理**：老词表的 0.926 是模型**训练出来的自信**，不是新 token 该有的起点。码本方向与 hidden
只是**部分**对齐（R²=0.40），范数一大，未被对齐的那 60% 就变成大幅随机 logits，淹没正确答案。

> **尺度是放大器 —— 方向对错都被它放大。**

**修正后的做法**：对齐 *resize 默认给新 token 的范数*（写入前实测 `emb.weight[orig:].norm().mean()`）。
这样与基线**同起点，唯一变量只剩方向**。实测该点 loss 13.18 < 基线 15.66 —— **方向确实带信息**。

### 4.2 其它实现细节

| 细节 | 处理 |
|---|---|
| code ↔ token 映射 | 不靠"猜 +1 偏移"，从 `codes[i,lv]` + `index.json` 反推并**断言自洽** |
| `<d_*>` 的 15 个消歧 token | **无码本对应**（覆盖 768/783 行）→ 保持随机方向，但尺度与其它新 token 对齐 |
| tie 红利 | 写 `emb.weight` 自动同步 `lm_head`，输入/输出两侧同时获得语义初值 |
| 承重校验 | 写入后断言新 token 行范数落在目标 ±50% 内，否则报错退出 |

### 4.3 训练后 embedding 几乎没动 —— 码本给的基本就是终点

对比 E2 的最终 checkpoint 与码本初值：

| | 结果 |
|---|---|
| 范数 | 0.3026 → **0.3238**（仅 ×1.07） |
| **cos(码本初值, 终值)** | **+0.8956**（中位 +0.9068，最低 +0.7481） |
| 完全偏离（\|cos\|<0.1）的行 | **0 / 768** |

> **新 token 的 embedding 在训练中只旋转了约 26°，范数几乎没变。**
> **码本不是"给个还行的起点"，它给的基本就是终点，训练只是微调。**
>
> 这解释了 1.82× 的收敛加速：**模型不需要"学" SID 语义，只需要"确认"它。**

**顺带验证了尺度选择**：两种初始化训练后都收敛到 ~0.32–0.34（老词表是 0.9262），
**0.3026 这个起点恰好落在收敛点附近**。

### 4.4 embedding 梯度掩码（`lora_freeze_old_emb=True`）

E1/E2/E3 三次实验用的都是这一套：**embedding 整块可训练，但只让 783 个新行动。**

**做法** —— 不冻结整块，而是注册一个梯度钩子把老行的梯度清零：

```python
embedding_layer.weight.requires_grad = True          # 整块可训练
if lora_freeze_old_emb:
    def mask_grad(grad):
        grad[:original_vocab_size].zero_()           # 前 151669 行梯度清零
        return grad
    embedding_layer.weight.register_hook(mask_grad)
```

**效果**：预训练词表的 151669 行保持原样，只有 783 个 SID token 行更新。
（既不是"完全冻结"，也不是"全词表放开"——是**只训新 token 行**。）

**为什么需要**：SFT 数据是单领域（工业与科学类目），全词表放开训练有**覆盖预训练语义**的风险；
而新 token 又必须能学，否则 SID 永远出不来。掩码是这两者之间的折中。

#### ⚠️ 边界必须是 `len(tokenizer) = 151669`，不是 `config.vocab_size = 151936`

783 个 SID token 里有 **267 个是"复用空槽位"**（全部 256 个 `<a_*>` + 11 个 `<b_*>`）——
它们的 id 落在原始词表的 padding 区，**并不是 resize 真正新增的行**。

用 `config.vocab_size`(151936) 当掩码边界，会**静默冻结整个 SID 第一层**（256 个 `<a_*>` 全部不更新），
训练照跑、loss 照降，但模型永远学不会生成第一个 SID token。

**证据**：这 267 行的 std = 0.029，而从未被训练过的 padding 行 std = 0.0095 ——
说明它们是预训练时留下的、从未被更新过的空槽。

#### ⚠️ 掩码**不省内存**（实测）

Adam 按**整块 tensor** 分配状态，与是否掩码无关。embedding 的全部开销（bf16）：

| 项 | 大小 |
|---|---|
| 参数 | 297.8 MiB |
| 梯度 | 297.8 MiB |
| Adam `exp_avg` | 297.8 MiB |
| Adam `exp_avg_sq` | 297.8 MiB |
| **合计** | **1191 MiB ≈ 1.16 GiB** |

> **掩码是行为约束开关，不是显存优化。**
> **推论：`FREEZE_OLD_EMB=False` 是一个零成本的消融点**（内存完全相同，只改行为）。

（实测佐证：`optimizer.pt` = 672.8 MiB = embedding 的 bf16 Adam 状态 595.5 MiB + LoRA 的 fp32 状态 77.0 MiB，逐字节吻合。）

#### ⚠️ 实现顺序：必须"先 PEFT、后打开 embedding"

PEFT 的 `get_peft_model()` 会调用 `_mark_only_adapters_as_trainable()`，**冻结所有非 `lora_` 参数**：

```
get_peft_model()  →  再打开 embedding.requires_grad  →  再注册掩码
```

**顺序反了会静默冻结全部 SID embedding** —— 训练照跑、loss 照降，但 SID 永远学不出来。
（代码里加了运行期断言兜底：`assert embedding_layer.weight.requires_grad`，
以及守恒律校验 `total_trainable == lora_trainable + emb_trainable`。）

## 5. 副产品：一批实测数据（可复用的结论）

### 5.1 显存公式：每 token ≈ 4.8 MiB

```
峰值显存 ≈ 1.9 GiB（参数+优化器，固定） + N × 4.8 MiB      N = micro × 批内实际 seq
```

**分解**（实测，非估算）：

| 组成 | MiB/token | 推导 |
|---|---|---|
| **logits 链路** | **2.62** | 18 字节/元素 × V(152452) |
| **28 层激活值** | **1.96** | 实测，N≥1024 时稳定 |
| 其它 | ~0.2 | 反向 workspace |

**logits 链路的 18 字节/元素**（隔离实测，V=152452）：

| 张量 | dtype | 字节/元素 |
|---|---|---|
| lm_head 输出 | bf16 | 2 |
| `.float()` 上采样副本 | fp32 | 4 |
| cross_entropy 前向内部 | fp32 | 4 |
| 反向梯度 ×2 | fp32 | 8 |
| **合计** | | **18** |

**两个重要推论**：
1. **注意力二次项可忽略**：实测同 N 下 L 取 128/256/512，激活显存**完全相同** → 成本只由 `N = B×L` 决定
2. **词表维度占绝对主导**：hidden 侧 2 KB/token vs logits 侧 2.62 MiB/token = **1340 倍**

四条预测与历史探针实测全部吻合，含"micro=32 在 seq=256 OOM"。

### 5.2 周期显存打点是**缓存水位**，不是活张量峰值

`sft.py` 的 `PeriodicEmptyCache` 打印 `reserved` 发生在 `empty_cache()` **之前**，所以：

```
reserved  19.84 GiB   ← 分配器缓存的最高水位（含碎片）
allocated  1.87 GiB   ← 此刻真正存活
真实活张量峰值 ~12.7 GiB（实测外推）
```

**约 7 GiB 是分配器碎片**——训练分配几万个大小各异的小张量，按 size-bucket 缓存着。

### 5.3 为什么 LoRA 在单卡上省不动显存

| | 全参（zero2 / 4 卡） | LoRA（1 卡） |
|---|---|---|
| reserved/卡 | 20.38 GiB | 19.84 GiB |
| 每步（同全局 batch） | 3.54 s | 9.77 s |

**逐卡算账**：

```
每个被优化的参数 = 2B(梯度) + 8B(Adam m+v) + 4B(主权重,仅DS) = 14 字节
                    ↑ 优化器状态是梯度的 4 倍

全参（4卡分片）每卡：参数 1.2 + 梯度 0.30 + 主权重 0.60 + Adam 1.20 = 3.30 G
LoRA（1卡无分片）：  参数 1.2 + 梯度 0.32 + Adam 1.33           = 2.85 G
差 = 0.45 G   ←  实测 0.54 GiB
```

> **核心洞察：LoRA 和 ZeRO 分片作用在同一处（优化器状态），收益不可叠加。**
>
> 而 LoRA 唯一能动的"参数"那 12%，在总显存里根本排不上号——**瓶颈是激活值和 logits 链路（~55%），与可训练参数量无关。**

**embedding 的全部开销（参数 + 梯度 + 优化器）共 1.16 GiB**，是当前 LoRA 里最大的一块可优化项
（Adam 按整块 tensor 分配状态，**梯度掩码不省内存**）。
其中"冻结 embedding"能省掉的是**梯度 + 优化器 = 893 MiB ≈ 0.87 GiB**（参数本身要留着做前向，省不掉）。

### 5.4 精度图景（bf16/fp32 实际分布）

| 成分 | 全参 SFT（zero2） | LoRA（无 DS） |
|---|---|---|
| 计算副本 | bf16 | bf16 |
| **优化器状态** | **fp32** | LoRA 部分 fp32 / **embedding 部分 bf16** |
| fp32 主权重 | 有（ZeRO 维护） | 无 |
| 前向的 fp32 点 | 4 处（RMSNorm 方差 / attn softmax / RoPE / CE logits 上采样） | 同 |

**关键澄清**：HF Trainer 的 `bf16=True` **不转换模型 dtype**（实测 fp32 建的模型训练完还是 fp32），
它只是通过 accelerate 把 `autocast(bf16)` 焊进 `model.forward`。**真正决定参数精度的是加载时的 `dtype=`。**

## 6. 环境与工程记录

### 6.1 单卡适配

本机只有 **1 张 RTX 5090（32.6 GB）**，而 `sft.sh` 硬编码 `NPROC=4` / `micro 16` / 输出到主线锚点 `outputs_ds`。
新增 `sft_cb.sh` 与两道守卫：

| 守卫 | 作用 |
|---|---|
| `OUTPUT_ROOT` 不许指向 `outputs_ds` | 防止覆盖 RL 起点模型 |
| `micro` 必须整除 1024 | 防止全局 batch 静默变小、破坏可比性 |
| `NPROC` ≤ 可见 GPU 数 | **已实际拦下 2 次错误** |

### 6.2 抗中断：队列与断点续跑

本机在这条实验线上**意外停机过两次**（2026-09-14、2026-09-16），容器被整体重启，
tmux server 连同子进程一起被杀——既没有 traceback，也没有 `[EXIT]` 标记。

**第一次（09-14）**：把跑到 28% 的测试集评估全废了（`evaluate.py` 只在**全部跑完**后写一次 JSON）。
对策：
- **评估分 8 块**顺序跑、每块各自落盘 → 再停机最多丢 1 块（~4 分钟）
- **`temp/run_cb_experiments.sh`** 串联多阶段，每阶段"已完成则跳过"

**第二次（09-16，E5 跑到 2602/2760）**：续跑时发现了一个**必须知道的问题**。

#### ⚠️ 本项目的 `--resume_from_checkpoint` 是**有损**的

代码库里有一条既有补丁（为省显存）：

```
[MONITORING] 跳过 optimizer/scheduler 加载（显存限制），仅恢复模型权重
```

于是 resume 时：

| | 是否恢复 |
|---|---|
| 模型权重 | ✅ |
| **优化器状态（Adam 动量）** | ❌ **丢失，从零开始** |
| **scheduler 状态** | ❌ **丢失 → warmup 重跑** |

**实测证据**：续跑后 lr 从 **0.0 重新爬升**

```
lr = 0.0 → 5e-06 → 1e-05 → 1.5e-05 → 2e-05 → 2.5e-05 → 3e-05 → 3.5e-05 …（每步 +5e-06）
而 checkpoint-2484/scheduler.pt 里的正确值应是 1.007e-05 并继续衰减
```

**后果**：末尾 276 步会跑在 ~1e-04，**比正确值高 10 倍**，污染结果。
**且更危险**：`save_total_limit=4` 会在后续两次存档时把干净的 best（checkpoint-2208）**轮换删掉**。

**处置**：停掉续跑，改用停机前训练出的**干净 best**（step 2208, eval_loss 2.4043）手动 merge：

```bash
python temp/merge_lora_ckpt.py <checkpoint目录> <输出目录>   # 逐行复刻 sft.py 的 merge 路径
```

这与 `load_best_model_at_end=True` 下 trainer 的选择一致（best 之后 2346/2484 均未改善）。
E5 的 18 个 eval 点**全部来自停机前的正常训练，未受污染**。

> **教训**：**"有 resume 功能" ≠ "resume 是无损的"。** 中断恢复前必须核对
> 优化器/scheduler 是否真的恢复了——最直接的信号就是**看 lr 走势是否连续**。

### 6.3 踩过的坑（值得记住）

1. **`set -e` 陷阱**：`[ -n "$VAR" ] && echo ...` 在变量为空时整条返回 1，**直接杀脚本**
2. **"已切分则跳过"判据错误**：凭 `0.csv` 存在就跳过，结果上一版遗留的**全量** CSV 被误判成"已切分"
   → 判据必须是"**本脚本写的**配置文件存在且一致"
3. **长跑前必须冒烟并核对首步指标**：尺度 bug 就是靠"首步 loss 29.76 vs 基线 6.80"抓到的

## 7. 待验证 / 下一步

### 7.1 打乱码本分配的对照实验（E5）—— **已完成 ✅**

**这是当前结论唯一的软肋。** 我们证明了"**码本方向 > MVN 随机方向**"（初始 loss 13.18 vs 15.66），
但 MVN 对照只控制了二阶统计量，**没控制"方向本身的分布形状"**。

**实现**（`--init_new_emb codebook_shuffled`）：把码本向量在**同一级内错位重排**
（拒绝采样强制 derangement，无不动点）——**向量集合、范数、层级结构全不变**，
只破坏"哪个语义向量给了哪个 token"。

**判读标准**：

| 打乱后的结果 | 说明 |
|---|---|
| ≈ 正确码本 | 起作用的是"**像真 embedding 的方向分布**"，语义对应无关 |
| ≈ resize（明显变差） | **语义对应真的起作用** |

#### ⚠️ 预检已给出信号（单 batch 初始 loss）

| 初始化 | 初始 loss |
|---|---|
| resize 基线 | 15.657 |
| 码本（正确） | **13.175** |
| **码本（打乱）** | **13.765** |

**打乱后明显偏向"正确"一侧，而不是回到 resize** —— 初步提示**收益里很大一部分来自方向分布**。

#### ⚠️ 但该对照有一个固有局限

验证输出显示：

```
两两 cos（正确 vs 打乱）= +0.2796     ← 不是 0
```

**码本向量本身不是各向同性的** —— 同一级的 256 个 k-means 质心围绕一个**共同方向**聚着。
所以"打乱"之后，向量仍然指向"SID 大致该在的区域"，只是偏离了这个 token 精确该在的位置。

**这恰恰就是我们要测的问题**：

> **token 级别的精确对齐重要，还是"落在 SID 区域里"就够了？**

#### 结果（2026-09-16）

| | HR@1 | HR@3 | HR@5 | HR@10 | HR@20 | HR@50 | NDCG@50 |
|---|---|---|---|---|---|---|---|
| 正确码本（E2） | 0.037617 | 0.046279 | 0.051352 | 0.059952 | 0.073130 | 0.095774 | 0.055299 |
| **打乱（E5）** | **0.036503** | **0.044670** | **0.049929** | **0.058900** | **0.070470** | **0.093609** | **0.053856** |
| LoRA 基线（E1） | 0.015406 | 0.026047 | 0.031244 | 0.041824 | 0.057044 | 0.083153 | 0.036109 |

| 对比 | HR@1 | HR@50 | NDCG@50 |
|---|---|---|---|
| **E5 vs E2**（打乱 vs 正确） | **−3.0%** | **−2.3%** | −2.6% |
| E5 vs E1（打乱 vs 基线） | +136.9% | +12.6% | +49.1% |
| E2 vs E1（正确 vs 基线） | +144.2% | +15.2% | +53.1% |

**"E2 相对于基线的提升，被打乱保住了多少"**：

```
HR@1 : E2−E1 = +2.221pp；E5−E1 = +2.110pp  →  保住 95.0%
HR@50: E2−E1 = +1.262pp；E5−E1 = +1.046pp  →  保住 82.8%
```

#### 结论：两个机制都真实存在，但**分布效应占主导**

1. **主要机制是"方向分布"** —— 打乱保住了 **83–95%** 的提升。
   即：**把新 token 放进"SID 该在的向量区域"就已拿到大部分收益**，精确的 token↔向量对应不是必要条件。

2. **但 token 级语义仍有一个小而稳的增量** —— E5 在**六个 K 上全部为负**（−1.8% ~ −3.6%），
   方向一致，不像噪声。这部分（约 2–3%）可以归因于**真正的语义对应**。

#### ⚠️ 又一次印证：eval_loss 与检索指标脱节

| | best eval_loss | HR@50 |
|---|---|---|
| 正确码本（E2） | 2.4151 | **0.095774** |
| 打乱（E5） | **2.4043** ← 更好 | 0.093609 ← **更差** |

**训练期 E5 的 eval_loss 全程领先 E2，测试集却输了 2.3%。**
这是本文档第三次观察到同样的现象（§3.3、§8.1）——**SFT 的 eval_loss 不能当检索质量的代理指标**。

#### 诚实的边界

- **单 seed**。−2.3% 的差距虽在 6 个 K 上方向一致，但无重复实验，无法给置信区间
- 码本向量**本身有共同方向**（正确 vs 打乱 cos = +0.28），所以打乱**并未完全破坏信号**——
  这是该对照的固有局限，"83–95%"应当理解为**上界性质的估计**

#### 训练中断说明

E5 跑到 2602/2760 时服务器意外关机，详见 §6.2。最终结果取自停机前训练出的干净 best
（checkpoint-2208），18 个 eval 点全部未受污染。

### 7.2 冻结 embedding（由 §4.3 直接推出）

§4.3 显示训练几乎没改方向（cos 0.896）。**那冻结它大概也差不了多少，
却能省掉 embedding 的梯度 + 优化器状态 = 297.8 × 3 = 893 MiB ≈ 0.87 GiB**
（参数本身要留着做前向，省不掉）——这是当前 LoRA 里最大的一块可省项。

需要一个 `--lora_freeze_new_emb` 开关（注意与现有的 `lora_freeze_old_emb` 正交：
后者掩掉老行、前者要连新行一起冻）。

### 7.3 其它消融（按性价比）

| 消融 | 接口 | 回答什么 |
|---|---|---|
| lr 扫描 | `LR=2e-4 bash sft_lora.sh` | 1e-4 是**未调优**起点 |
| `FREEZE_OLD_EMB=False` | 同上 | 零成本（内存相同） |
| r ∈ {8,16,32} 配 alpha=2r | `LORA_R=8 ...` | 低秩容量是否瓶颈 |

### 7.4 一个未解释的现象

§4.3 显示新 token 的范数始终只有老词表的 **1/3**（0.32 vs 0.926）。
这可能意味着**模型对 SID token 的预测始终不够"坚决"**——
而恰好对应 HR@1（91.3%）比 HR@50（99.2%）差得多：**排序靠后能进，但挤不到第一。**
（需看 logits 分布验证。）

## 8. 结论（五个实验全部完成，2026-09-16）

### 8.1 五路对比总表（测试集 16163 条）

| | HR@1 | HR@3 | HR@5 | HR@10 | HR@20 | HR@50 | 占全参 HR@50 |
|---|---|---|---|---|---|---|---|
| **全参基线（E3）** | 0.041205 | 0.047207 | 0.051723 | 0.061065 | 0.074120 | **0.096579** | 100% |
| 全参+码本（E4） | 0.040958 | 0.046774 | 0.050486 | 0.059952 | 0.072883 | 0.094846 | 98.2% |
| **LoRA+码本（E2）** | **0.037617** | **0.046279** | **0.051352** | **0.059952** | **0.073130** | **0.095774** | **99.2%** |
| LoRA+打乱（E5） | 0.036503 | 0.044670 | 0.049929 | 0.058900 | 0.070470 | 0.093609 | 96.9% |
| LoRA 基线（E1） | 0.015406 | 0.026047 | 0.031244 | 0.041824 | 0.057044 | 0.083153 | 86.1% |

**相对变化**：

| 对比 | HR@1 | HR@50 | NDCG@50 |
|---|---|---|---|
| 全参+码本 vs 全参基线 | −0.60% | −1.79% | −1.45% |
| **LoRA+码本 vs LoRA 基线** | **+144.2%** | **+15.2%** | **+53.1%** |
| LoRA+打乱 vs LoRA 基线 | +136.9% | +12.6% | +49.1% |
| LoRA+打乱 vs LoRA+码本 | −3.0% | −2.3% | −2.6% |

### 8.2 核心结论

> **① 码本初始化对 LoRA 是决定性的，对全参几乎无影响。**
>
> **② 它把 LoRA 从「明显不如全参」拉到「基本持平全参」**：
> HR@50 从全参的 86.1% → **99.2%**，HR@1 从 37.4% → **91.3%**。
>
> **③ 并且 LoRA+码本（0.095774）与全参+码本（0.094846）几乎重合**
> （差 0.96%，相对全参）—— **两条线被码本拉到了同一个水平**。

**机制解释**（与 §0.3 的诊断闭合）：

```
LoRA 的瓶颈 = 容量不足，学不出 SID 符号系统   → 码本补上这块 → 巨大提升
全参的容量本来就够，自己能学出 SID 语义        → 码本多余，甚至略拖累
```

**这正好是我在 E1 之后提出的假说，现在两个方向都验证了：**
> **问题的根源是"容量不足"，不是"初始化不好"。** 码本的作用是**把"学符号"这件事外包出去**，
> 所以只对"学不动"的那一方（LoRA）有效。

**④ 机制归因（E5 打乱对照）—— 两个机制都真实存在，分布效应占主导**（详见 §7.1）

```
打乱后仍保住 E2 提升的：HR@1 95.0% / HR@50 82.8%
残余的 2–3%（六个 K 上方向一致）：可归因于 token 级精确语义对应
```

> **把新 token 放进"SID 该在的向量区域"就已拿到大部分收益**；但**精确的 token↔向量对应
> 仍有一个小而稳定的增量**。码本的价值是两部分叠加，不是单一机制。

### 8.3 必须同时声明的限定

1. **单 seed、单类目**（Industrial_and_Scientific），无重复实验。
   E5 vs E2 的 −2.3% 虽在六个 K 上方向一致，但**无置信区间**
2. `E1 vs E2 vs E5`、`E3 vs E4` 是**干净 A/B**（唯一变量 = 初始化方式）；
   但 **"LoRA 追平全参"是跨配置比较**（LoRA 单卡 vs 全参 4 卡），严格性更弱
3. **打乱对照有固有局限**：码本向量本身有共同方向（正确 vs 打乱 cos = +0.28），
   打乱并未完全破坏信号 → §8.2④ 的"83–95%"应理解为**上界性质的估计**
4. **码本初始化会让 LoRA 早停**（epoch 8.5 vs 基线 10.0），比较时注意训练量不同
